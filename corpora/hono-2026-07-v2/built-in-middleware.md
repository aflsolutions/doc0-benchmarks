Built-in middleware in Hono provides a standardized interface for augmenting the request/response lifecycle. Designed as asynchronous functions, they sit between incoming requests and route handlers, enabling cross-cutting concerns like security headers, CORS, CSRF protection, and IP access control to be implemented with minimal boilerplate.

Each middleware adheres to a consistent pattern: it accepts a `Context` object and a `next` function to trigger subsequent handlers. This design allows them to modify the `Context`, validate inputs before execution, or intercept and modify the final response object generated by a route.

The architecture emphasizes composability. Since middleware typically yields a handler function conformant to Hono's middleware model, they can be mounted globally using `app.use('*', middleware())` or scoped to specific paths, ensuring that concerns are applied only where necessary. This granular control allows developers to maintain clean, modular application logic while ensuring robust security and utility behavior across diverse runtime environments.

## Security Middleware

Security middleware enforces best practices by manipulating HTTP headers and validating incoming request properties against security policies.

### Secure Headers
The `secureHeaders` middleware manages headers that enhance application security, including `Content-Security-Policy` and `Permissions-Policy`. It implements a filter-based approach: predefined default headers (e.g., `X-Content-Type-Options: nosniff`) are applied unless overridden by user configuration.

The mechanism relies on a internal constant `HEADERS_MAP` mapping configuration keys to their standard HTTP header counterparts and default values. When `secureHeaders` executes, it evaluates these options and constructs a headers array. Crucially, the middleware performs late-stage injection of security headers into the `c.res` object (line 223), ensuring that user-defined headers in subsequent route handlers do not accidentally bypass these critical security settings.

> [!NOTE]
> The `NONCE` generator (lines 131-135) uses `crypto.getRandomValues`. When used within a CSP policy, it ensures generated nonces are stored in the `Context` for use by template engines or UI components.

Sources: [src/middleware/secure-headers/secure-headers.ts:94-224](https://github.com/honojs/hono/blob/main/src/middleware/secure-headers/secure-headers.ts#L94-L224)

### Cross-Site Request Forgery (CSRF)
The `csrf` middleware prevents unauthorized state-changing requests (e.g., POST, DELETE) by validating either the `Origin` header or the `Sec-Fetch-Site` header. It implements a permissive logic: if either the origin or the fetch-site is deemed "allowed," the request proceeds.

The check sequence is:
1. `isAllowedSecFetchSite` (Chain: `csrf` → `isAllowedSecFetchSite` → `isSecFetchSite`).
2. `isAllowedOrigin` (Customizable callback).

If the request is not a "safe" method (GET, HEAD) and fails both checks, the middleware throws an `HTTPException(403)`.

Sources: [src/middleware/csrf/index.ts:14-147](https://github.com/honojs/hono/blob/main/src/middleware/csrf/index.ts#L14-L147)

## Auth Middleware

### IP Restriction
The `ipRestriction` middleware restricts access based on IP address lists. It leverages `buildMatcher` to compile CIDR ranges and static IPs into optimized lookup tables.

Mechanism:
- `buildMatcher` (lines 51-167) differentiates IPv4 and IPv6 rules using bitwise operations (`1n << BigInt(prefix)`).
- When a request hits, `ipRestriction` retrieves the client IP via an IP configuration value lookup.

Sources: [src/middleware/ip-restriction/index.ts:51-167](https://github.com/honojs/hono/blob/main/src/middleware/ip-restriction/index.ts#L51-L167)

The internal deny matcher compiled from your `denyList` is evaluated first; if it matches the client address, the request is blocked.

Sources: [src/middleware/ip-restriction/index.ts:249-255](https://github.com/honojs/hono/blob/main/src/middleware/ip-restriction/index.ts#L249-L255)

If not denied, the internal allow matcher compiled from your `allowList` is checked (if an `allowList` exists). If the IP does not match the allowed definitions, access is denied by default.

> [!CAUTION]
> The order of rules within `allowList` or `denyList` does not imply precedence; all rules are compiled into a set-based matcher that determines access regardless of array position.

Sources: [src/middleware/ip-restriction/index.ts:256-277](https://github.com/honojs/hono/blob/main/src/middleware/ip-restriction/index.ts#L256-L277)

## Utility Middleware

### Method Override
The `methodOverride` middleware allows browsers to perform non-GET/non-POST operations (like PUT, PATCH, DELETE) by tunneling them through standard HTML forms or headers.

Mechanism:
1. It detects an incoming `POST` request.
2. It parses the body (`formData` or `URLSearchParams`) or header (e.g., `X-HTTP-Method-Override`).
3. It identifies the target method and rewrites the request object.
4. It calls `app.fetch()` recursively with the rewritten request to route the request to the correct handler.

Sources: [src/middleware/method-override/index.ts:60-137](https://github.com/honojs/hono/blob/main/src/middleware/method-override/index.ts#L60-L137)

### CORS
The `cors` middleware handles Cross-Origin Resource Sharing by injecting `Access-Control-*` headers.

Key mechanics include:
- Finding the allowed origin: An internal lookup that determines the allowed origin based on the request header.

Sources: [src/middleware/cors/index.ts:72-84](https://github.com/honojs/hono/blob/main/src/middleware/cors/index.ts#L72-L84)

- `OPTIONS` request handling: When an `OPTIONS` request is received, it returns a `204 No Content` response immediately with appropriate headers, preventing the request from proceeding to actual route handlers.

Sources: [src/middleware/cors/index.ts:114-148](https://github.com/honojs/hono/blob/main/src/middleware/cors/index.ts#L114-L148)

## Design Trade-offs

| Design Choice | Benefit | Cost |
| :--- | :--- | :--- |
| **Middleware Chain** | Decoupled concerns, easy to plug/unplug | Middleware order affects behavior and security |
| **Context-based API** | Unified access to request/env/vars | Heavy reliance on `Context` object instances |
| **Pre-compiled Matchers** | Faster lookups for large IP lists | Increased memory usage for compiled sets/bitmasks |

## Worked Example

This example demonstrates enabling security headers and CSRF protection in a Hono application.

```typescript
import { Hono } from 'hono'
import { secureHeaders } from 'hono/secure-headers'
import { csrf } from 'hono/csrf'

const app = new Hono()

// Apply CSRF protection globally
app.use('*', csrf())

// Apply security headers
app.use('*', secureHeaders({
  contentSecurityPolicy: {
    defaultSrc: ["'self'"],
  }
}))

app.post('/update', (c) => {
  return c.json({ status: 'success' })
})
```
